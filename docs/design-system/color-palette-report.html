02 · What changes from area to area

The app is unified in mood, not in exact values.

These are the palettes that appear in active-looking client paths. They are not unused theme previews. The repeated pattern is “Apple dark, then locally adjusted,” with a few screens that still carry older or light-world assumptions.

Mostly aliases the global system, with local fallback colors for workflow logs and recovery states.

Gmail is a palette crossroads

The Gmail stylesheet contains light Gmail-like fallbacks such as #fff and #3c4043, a teal fallback around #1a7a6d, and later indigo tooling around #6366f1, #1a1a2e, and #1e1e2e.

Calendar and data colors are special cases

Calendar events, shipment states, image grades, avatars, and provider marks use direct colors. They can remain distinct, but they need an explicit “external data / identity / visualization” classification so they do not quietly become new semantic colors.

Read this as “unified, not uniform.” The app does not need every external data color to become Apple blue. It does need a visible rule for which colors are product meaning, which are provider identity, and which came from data outside the app.

03 · Judgment

The good, the bad, and the ugly.

This is the part to use when deciding what to preserve and what to harden.

Good · strong visual foundation

  • Clear hierarchy: four dark surface levels make panels and popovers understandable.
  • Recognizable meaning: blue, green, yellow, and red already have useful status roles.
  • Readable primary text: #f5f5f7 and #a1a1a6 work well on the dark baseline.
  • Existing variables: many newer components can be migrated by changing aliases, not every rule.

Bad · the system has competing authorities

  • Slate versus Apple dark: the documented baseline and the strongest CSS override disagree.
  • Local copies drift: #0a84ff, #4a9eff, #6ea1f7, and #3b82f6 all compete as “blue.”
  • Fallbacks change the language: missing variables can fall into Slate, light, teal, or indigo values.
  • Theme selection is uncertain: normal inline theme variables may lose to global !important tokens.

Ugly · users may see contradictory signals

  • White on primary blue: several blue action treatments are likely too low-contrast for normal-sized text.
  • Tertiary gray is too dim: #636366 on #1c1c1e is a metadata-only color, not general body text.
  • Light cards in a dark app: invoice matching and Gmail fallbacks can look imported rather than integrated.
  • Global fights: giant override layers force components to defend themselves with more !important.

04 · Hardening map

What to fix first.

Contrast checks worth acting on

Primary text on background#f5f5f7#1c1c1e15.6:1 · strong
Secondary text on background#a1a1a6#1c1c1e6.6:1 · good
Tertiary text on background#636366#1c1c1e2.8:1 · too dim
White text on primary blue#fff#0a84ff3.4:1 · review
Dark text on local blue#4a9eff#08233f5.8:1 · safer

Ratios are static token checks, not a substitute for rendered browser inspection across states.

Recommended sequence

Declare one baseline.

Formally choose Apple dark or Slate. The current source behaves most like Apple dark.

Make semantic tokens win.

Put action, text, surface, status, focus, and disabled tokens in one authoritative layer.

Turn local tokens into aliases.

Keep feature names such as --ag-accent only when they point to shared meanings.

Approve exceptions.

Keep provider brands, calendar events, shipment data, and grades in a documented external-data lane.

Remove cascade escalation.

Reduce the global !important layer so components no longer need defensive overrides.

Priority decision: Do not start by picking more colors. First decide which layer is allowed to define what a color means. Then fix contrast and migrate the highest-drift areas: overhaul, Agents, Gmail, Calendar, invoice matching, and the agent-test modal.
