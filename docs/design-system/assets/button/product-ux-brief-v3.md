# Button Documentation Cover — Focused Product/UX Correction

## User goal

Understand what Button is and see one authoritative example immediately, without reading implementation language or looking through an oversized empty display frame.

## Entry and next action

The route opens on a composed specification cover. The reader sees the specification label, `Button`, one plain-language definition, and one live production Button. Scrolling continues into the already-approved visual family.

## Information architecture

The existing sequence remains: identity, visual family, then detailed reference. This correction changes the quality and proportion of the identity stage, not the page's chapter model.

## Stable frame

The documentation shell, page width, navigation, following chapters, and production Button remain unchanged.

## Initially visible

Only the specification label, title, short definition, and one primary large `Save changes` Button. The Button is the visual subject; no specimen border, facts, badges, API, or secondary examples appear.

## Progressive disclosure

The next section, `Button at a glance`, follows directly after the cover and remains discoverable without scrolling through a vacant panel.

## State matrix

The cover is static and uses one resting live Button. Loading, disabled, recovery, confirmation, focus, and reduced motion remain demonstrated later in the page and are unaffected.

## Continuity

Route, anchors, scroll order, focus behavior, and later live fixtures remain stable.

## Wording

Use: `Button lets people initiate an action while communicating its priority, consequence, availability, and progress.` Avoid implementation terms such as `native` and `caller-labelled` in the cover definition.

## Trust and privacy

The specimen contains generic fixture wording and performs no external action.

## Desktop and mobile

Desktop uses a centered editorial composition with a deliberately scaled full-width Button inside a bounded placement wrapper—not a decorative specimen card. At exactly 390px, the complete identity stage remains readable, balanced, reachable, and free of horizontal overflow.

## Keyboard and accessibility

The production Button remains a native focusable control with its existing visible focus treatment. Reading and DOM order remain label, title, definition, specimen.

## Reduced motion

No new motion is introduced.

## Production versus development

No developer controls, measurements, diagnostics, or implementation metadata appear in the cover.

## Visual craft and Slate fit

Use Slate typography, ink, accent, and hairline tokens. Quality comes from optical balance, concise copy, precise measure, and purposeful whitespace. Do not use a gradient, glow, glass, shadow spectacle, or a large empty bordered container.

## Scope and approval triggers

Allowed: Button documentation cover markup, page-specific CSS, its focused assertion, current evidence, release record, and the reusable skill rule exposed by the rejection. Changing the shared docs shell, Button contract, later specification content, or other component pages requires renewed approval.
